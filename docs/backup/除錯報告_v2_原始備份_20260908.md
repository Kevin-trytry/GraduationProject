## 一、結論摘要

**訓練端已排除。問題 100% 在部署端（燒錄 / 韌體 / 量化轉檔）。**

96×96 模型的訓練指標如下（來源：`model_output/gesture_model/results.csv`）：

| 指標 | 最終值（epoch 120）| 最佳值 | 判定門檻 | 結果 |
|------|-------------------|--------|---------|------|
| **mAP@0.5** | **0.98228** | 0.98487（ep 85）| > 0.75 | ✅ 遠超標準 |
| mAP@0.5:0.95 | 0.84974 | 0.85394（ep 117）| — | ✅ 極佳 |
| Precision | 0.97519 | 0.98431 | — | ✅ |
| Recall | 0.98350 | 0.98380 | — | ✅ |

補充健康度檢查：

- **無過擬合**：train box_loss 0.504 vs val box_loss 0.573，差距極小
- **收斂正常**：val/cls_loss 從 3.05 單調下降至 0.411，無反彈
- **epoch 111 損失突降屬正常**：Ultralytics `close_mosaic` 在最後 10 epoch 自動關閉 mosaic 增強所致，非異常
- **patience=15 未觸發**：跑完整 120 epoch，模型至最後仍在進步

### 逐類別能力的反推

results.csv 只有整體平均值，但可以反推：11 類平均 mAP50 = 0.982。即使假設表現最好的 0/2/6 三類為滿分 1.0，其餘 8 類仍須各自達到約 0.975 才能撐出此平均值。

**因此「cls4 / cls5 / cls8 / cls9 學不到」的假設在 96px 模型上不成立。**

> ⚠️ 注意：`Pileline_3_firmware.md` §9 列出的「要靠訓練端解決」清單（cls4/5 補資料、cls2 偏斜、cls8 vs cls9 對比樣本等），是**上一版 192px 模型**的實測結論。96px 模型的訓練指標已大幅改善，這份清單需在取得 96px 有效實測數據後重新評估，不宜直接沿用。

## 二、四條待查路徑（按可能性排序）

前三條都只需檢視 UART log 即可分辨，不需修改任何程式碼。

### 路徑 1：燒到舊的 192px 模型快照 ★★最可能

**這是 Kevin 自己在 `Pileline_3_firmware.md` §6 寫下的已知陷阱：**

> ⚠️ `build_and_flash.py` 只認 `model_zoo` 底下那個固定檔名，**不會**自動抓最新的 `best_int8_vela.tflite`。拿到新模型要先跑 `deploy.py`，否則會燒到舊快照。

**機制**：若本次燒錄前未執行 `deploy.py`，`model_zoo/tflm_yolov8_od/` 底下仍是舊的 192px 模型，`build_and_flash.py` 會把它燒進 flash。韌體端已改為 96 → 依 `YOLOV8_OB_INPUT_TENSOR_WIDTH/HEIGHT` 推算期望 anchor 數 189，但模型實際是 **756** → 觸發 `cvapp_yolov8n_ob.cpp` 第 464–466 行的靜默 return：

```cpp
if (dfl_mode && yolov8_expected_anchors(input_w, input_h) != num_anchors) {
    return;   // 什麼都不印，boxes.size() 那行也不會執行
}
```

**為何這條排第一**：同一份文件 §8 記錄今天已發生過一次**方向相反的同類錯誤**——

> 2026-09-08 訓練端把 `IMAGE_SIZE` 從 192 改成 96 並重新匯出，韌體端沒同步 → 模型 189 anchors vs 韌體預期 756 → 對帳檢查每幀 `return`，板子完全不畫框、也沒有明顯錯誤訊息

第一次是「韌體 192 + 模型 96」。韌體改成 96 之後，若模型快照沒更新，就變成「韌體 96 + 模型 192」——**完全的鏡像版本，同一個靜默 return，同樣零框**。同一個坑反向踩第二次。

**判斷依據**：開機第一幀的 layout log

```
=== YOLOv8 OUTPUT LAYOUT (auto-detected) ===
  bbox  dims: [1, 64, ???]
  class dims: [1, 11, ???]
  num_classes=11  num_anchors=???  cls_layout=class-major  sigmoid=???
```

| `num_anchors` 值 | 結論 |
|-----------------|------|
| **189** | ✅ 模型正確，排除此路徑，往路徑 2/3 查 |
| **756** | ❌ **確認燒到舊的 192px 快照**，並會伴隨 `[ERROR] anchor 數不符` |

**修法**：

```powershell
python deploy.py                        # ★ 必須先跑，同步最新模型並改成正確檔名
python build_and_flash.py --port COM3
```

燒錄後立即確認 UART 的 `num_anchors=189`。

**輔助檢查**：`model_zoo/tflm_yolov8_od/` 底下的檔名應為 `gesture_yolov8n_96_vela_0xB7B000.tflite`。若仍是 `..._192_...`，即確認未執行 `deploy.py`。同時比對檔案時間戳與 `best_int8_vela.tflite` 是否一致。

### 路徑 2：大框過濾在 96 輸入下過度嚴格 ★

**位置**：`cvapp_yolov8n_ob.cpp` 第 276 行

```cpp
#define YOLOV8_MAX_BOX_AREA_RATIO 0.80f
```

**問題**：此參數的註解與 `Pileline_3_firmware.md` §3 的推導都以 **192** 輸入為基準。但 **DFL 的期望值以 grid cell 為單位，不隨輸入尺寸改變**：

| stride | 每邊距離 | 解碼框尺寸 | 192 輸入（門檻 29491）| 96 輸入（門檻 7373）|
|--------|---------|-----------|---------------------|-------------------|
| 8 | 7.5 × 8 = 60px | 120×120 | 面積 14400 → **通過** | 夾回 96×96 = 9216 → **被丟** |
| 16 | 7.5 × 16 = 120px | 240×240 | 被丟 | 被丟 |
| 32 | 7.5 × 32 = 240px | 480×480 | 被丟 | 被丟 |

在 96×96 之下，0.8 的面積門檻等於「邊長超過 86px（= √0.8 × 96）的正方形框就丟掉」。而訓練資料中手部佔畫面約 60–80%，**正確的手部框很容易超過 86px，連正確答案都被過濾掉**。

Kevin 文件 §7 的範例 log 本身就出現 `(96x96)` 的框被丟——那是 96 輸入下的整張畫面框，與此推導一致。

**判斷依據**：log 中是否大量出現

```
[filter] drop oversized box cls=? conf=??% (??x??)
```

- **大量出現且框尺寸接近 96×96** → 確認此路徑
- **完全沒出現** → 排除（代表根本沒有 anchor 通過門檻，或推理沒跑）

**修法**：先改為 `1.0f`（完全關閉）驗證，確認後再調至 `0.95f` 取平衡。

```cpp
#define YOLOV8_MAX_BOX_AREA_RATIO 1.00f
```

> 注意：`Pileline_3_firmware.md` §3 指出全畫面框與真實手部框的 IoU ≈ 0.52 > NMS 門檻 0.45，關閉過濾後大框會回頭吃掉正確框。因此 `1.0f` 只用於驗證，不可作為最終設定。若確認是此路徑，正確做法是把比例改為以輸入尺寸自適應，或直接調至 0.95f。

### 路徑 3：`AllocateTensors()` 靜默失敗

**位置**：`cvapp_yolov8n_ob.cpp` 第 174–193 行

```cpp
static tflite::MicroMutableOpResolver<2> yolov8n_ob_op_resolver;
yolov8n_ob_op_resolver.AddTranspose();
if (kTfLiteOk != yolov8n_ob_op_resolver.AddEthosU()) {
    xprintf("Failed to add Arm NPU support to op resolver.");
    return false;          // ← false = 0
}
...
if (yolov8n_ob_static_interpreter.AllocateTensors() != kTfLiteOk) {
    return false;          // ← false = 0，但 0 是「成功」的回傳碼！
}
```

**Bug 本體**：函式簽章為 `int cv_yolov8n_ob_init(...)`，成功時 `return ercode`（= 0）。`AllocateTensors()` 失敗時 `return false` 也等於 0，**呼叫端無法區分成功與失敗**。

**後果**：呼叫端誤以為初始化成功，但 `yolov8n_ob_int_ptr` 停留在 `nullptr`。而 `cv_yolov8n_ob_run()` 的整個推理區塊包在 `if (yolov8n_ob_int_ptr != nullptr)` 之內 → resize、Invoke、後處理全部跳過 → **連一行推理相關的 log 都不印**。

**為何這次可能發生**：`MicroMutableOpResolver<2>` 只註冊 `Transpose` 與 `EthosU`，代表 vela 編譯後的模型除 Transpose 外每個 op 都必須被 Ethos-U 接走。而 **vela 的 offload 判斷會隨張量尺寸改變**——192→96 之後，原本能進 NPU 的 op（Reshape、Split、Concatenation、Quantize 等）可能被判定留在 CPU。只要多出任何一個未註冊的 CPU-side op，`AllocateTensors()` 就失敗，且失敗得毫無聲音。

**判斷依據**：

| log 狀況 | 結論 |
|---------|------|
| 有 `initial done` 但**沒有** `yolov8 object detect invoke pass` | ✅ 確認是此問題 |
| 有 `yolov8 object detect invoke pass` | ❌ 排除 |

**輔助驗證**：檢視 `export_full_int8.py` 執行時 vela 的輸出報告：

```
Info: The following operators are placed on the CPU: ...
Total NPU operators: xx
Total CPU operators: xx
```

若 CPU operators 不為 0（或不只有 Transpose），即確認。

**修法**：

```cpp
static tflite::MicroMutableOpResolver<8> yolov8n_ob_op_resolver;   // 容量加大
yolov8n_ob_op_resolver.AddTranspose();
yolov8n_ob_op_resolver.AddReshape();      // 依 vela 報告補上實際需要的 op
yolov8n_ob_op_resolver.AddQuantize();
yolov8n_ob_op_resolver.AddDequantize();
if (kTfLiteOk != yolov8n_ob_op_resolver.AddEthosU()) { ... }
```

同時建議把兩處 `return false` 改為 `return -1`，讓失敗能被上層攔到。這是 Himax 原版就存在的問題，值得順手修掉。

### 路徑 4：sigmoid 判斷邏輯誤判（低機率）

**位置**：第 418–419 行

```cpp
const float cls_max_repr = (127.0f - (float)output_2_zeropoint) * output_2_scale;
const bool cls_is_logit = (cls_max_repr > 1.5f);
```

以「量化能表示的最大值是否 > 1.5」判斷 class tensor 是否為未過 sigmoid 的 logit。若新模型的量化參數使 `cls_max_repr` 落在 1.5 以下，`cls_is_logit` 會誤判為 false，門檻 0.20 將直接與**未過 sigmoid 的 raw logit** 比較。raw logit 若多為負值，全部 anchor 被 `continue` 掉，框數恰好歸零。

**判斷依據**：layout log 的 `sigmoid=` 欄位。Layout B（DFL raw）模式下**必須是 `YES (韌體補算)`**；若印出 `NO (模型已算)` 即為誤判。

參考值：192px 模型的 `scale=0.169, zp=4` → `(127−4)×0.169 = 20.8 > 1.5` → 正確判為 logit。96px 模型的量化參數需實際確認。


## 四、其他觀察（非本次問題，建議後續處理）

### Score Threshold 偏低
`Pileline_3_firmware.md` §4 記錄目前為 `0.20`，註解說明「模型重訓前的折衷值，原 0.15 太低，0.35 目前模型達不到」。

新模型訓練 Precision 0.975、Recall 0.984，量化後信心度應顯著提升。**零框問題解決後，建議調高至 0.35~0.50**，並重新評估該註解是否仍成立。

### 建議改用 Layout A
`Pileline_3_firmware.md` §2.2 指出 Layout A 量化精度較好（兩輸出各自 scale，而非共用），且**韌體完全不用改**，會自動走 A 分支。

目前 `export_full_int8.py` 的 Monkey Patch 只做 `return box, cls` 拆分，仍屬 Layout B（DFL raw）。若在 export 端加上完整的 split-output patch（DFL 解碼 + sigmoid 在匯出時完成），可望改善量化精度，同時省掉韌體端每幀的 softmax 運算。這是零框問題解決後值得優先嘗試的優化。

### 三端參數對接（已確認一致）

| 項目 | train.py | export_full_int8.py | cvapp | 狀態 |
|------|----------|---------------------|-------|------|

| NUM_ANCHORS | — | 189 | 自動推算 189 | ✅ |

**程式碼層面三端已完全對齊。剩下的是燒錄流程與後處理參數問題。**
