## 二、96 vs 192 對照實驗（上午）

唯一變因是模型。韌體程式碼、相機、輸入路徑、拍攝環境全部相同。

| | **96 模型** | **192 模型** |
|---|---|---|
| 輸出格式 | Layout B / DFL raw、189 anchors | Layout A / decoded、756 anchors |
| `best%` 最大 / 中位 | **7 / 1** | **90 / 24** |
| 通過門檻的幀數 | **0 / 157** | **143 / 247（58%）** |
| 實際畫出的框 | **0** | **140** |
| `[INPUT]` 亮度 mean | uint8 81 | uint8 84 |

`[INPUT]` 只差 3，兩邊的輸入傾印還原出來都是清晰可辨的手 —— **輸入路徑不是變因**。

**結論：96 那顆模型本身不可用。** 之後全部改用 192。

### 附帶驗證的韌體項目

「192 跑得動」這個事實一次驗證了整條鏈路：開機/arena、NPU 初始化、模型載入、`AllocateTensors`、相機、resize、RGB 通道順序、uint8→int8、輸出格式自動偵測、反量化、門檻換算、DFL 解碼、面積過濾、NMS。全程 0 個 `[FATAL]`。

## 三、★ 主要發現：幾何失真（letterbox）

### 問題

```
訓練圖片   1440 × 1440   正方形（手機 1:1 模式拍攝＝裁切，非壓扁）
Camera raw  320 × 240    4:3
模型輸入    192 × 192     ← 寬縮 0.600、高縮 0.800
```

韌體原本是**直接把 4:3 硬拉成 1:1**，水平方向被額外壓縮 **25%**。而 ultralytics 訓練與推論都用 letterbox（等比縮放 + 補灰邊），模型從沒看過橫向壓扁的手。

### 怎麼確認訓練圖是裁切而非壓扁

原始素材是混合的：`0/3/4/8/B.MOV` 是 1920×1080 (16:9)、`1/2/6.mov` 本來就是 1440×1440 (1:1)，抽出來的 jpg 全是 1440×1440。

拿同類別、兩段不同來源影片的**標註框長寬比**來比：

| 類別 | 來源 A | 來源 B | 比值 |
|---|---|---|---|
| 0 | 0.811 | 0.849 | 1.05 |
| 1 | 0.520 | 0.502 | 1.04 |
| 5 | 1.069 | 1.083 | 1.01 |
| 9 | 1.088 | 1.091 | 1.00 |
| B | 3.382 | 3.400 | 1.01 |

若是壓扁，16:9 來源的物體長寬比會變成原本的 0.5625 倍，比值應出現 **1.78** 左右。實際只有 **1.00~1.15** → **是置中裁切，幾何忠實**。

新的 3000 張是用手機 1:1 模式拍的（同樣是裁切），結論一致。

### 為什麼影響的是拇指

**拇指是唯一往水平方向伸出去的手指。** 被壓掉 25% 之後幾乎貼回手掌。

失敗類別的分佈本身就是獨立佐證：

| 手勢方向 | 類別 | 修正前 |
|---|---|---|
| 垂直 | 0 拳、1 食指、2 V、3 三指 | ✅ 正常 |
| **水平張開** | 4 四指、5 五指、**7/8/9 拇指外張** | ❌ 全部失敗 |

### 修正內容

`cvapp_yolov8n_ob.cpp`（備份 `.bak9_20260909`）

```c
#define YOLOV8_USE_LETTERBOX 1        // 設 0 可切回硬拉做 A/B
#define YOLOV8_LETTERBOX_PAD_VALUE 114
```

- **前處理**：整片填 114（與 ultralytics 相同的灰），等比縮成 192×144 寫進中間，上下各留 24 列灰邊
- **後處理**：座標先扣 `pad_y` 再換算回相機座標；夾邊與面積過濾改用有效區（192×144）
- **防呆**：`pad_x != 0`（直式來源）無法用位移指標寫入，會印警告並退回硬拉，不會寫壞記憶體

數學已用獨立編譯驗證：320×240→192×192 得 fit=192×144、pad_y=24；座標往返誤差 0 px；`-Wall -Wextra` 零警告。

## 四、Layout A 模型（傍晚，17:00 session）

Johnson 提供的 Layout A 模型規格確認無誤：

```
IN   [1, 192, 192, 3]
OUT  [1, 11, 756]  scale=0.00390625 (1/256) zp=-128   ← class，已 sigmoid
OUT  [1, 4, 756]   scale=1.3856      zp=-120          ← bbox，像素值
operators: ethos-u ×1                                  ← 零 CPU fallback
```

兩個輸出 scale 不同 ＝ 真正的 Layout A。也沒有做 permute，所以沒有多出 CPU 端的 Transpose。韌體自動偵測，不需要改任何程式碼。

### 結果

| | Layout B (16:45) | **Layout A (17:00)** |
|---|---|---|
| 偵測筆數 | 540 | 323 |
| 類別分布 | cls2 **230**、cls4 118、cls3 64 | cls4 **157**、cls3 79、cls2 **42** |
| 平均信心度 | 42% | **42%** |
| 最高信心度 | 93% | 92% |
| >70% 佔比 | — | 11% |

**cls2 這個黑洞從 230 掉到 42**，而 cls4 升到 157（最長 51 幀連續段落、最高 92%）。cls7 從 2 升到 11。

### ⚠️ 依序測試後的修正結論：Layout A 沒有比較好

17:00 那場 Kevin 是**依序比 1~9**（後半段才隨機測試），所以前 90 秒有明確的 ground truth。

**不是固定偏移**（排除類別索引錯位的可能），是真的分不出手指數量。

### 黑洞只是換了位置

```
letterbox 前          ：黑洞是 cls2（230 筆）
letterbox + Layout B  ：黑洞是 cls4（118 筆），但驗證到正確的 cls4 / cls3 / cls10
letterbox + Layout A  ：黑洞是 cls4（157 筆），依序測試下幾乎全錯
```

平均信心度兩者都是 42%、沒有變化。**原本預期「class 量化解析度好 14 倍會讓混淆類別分得開」，沒有實現** ——
再次印證瓶頸在模型的判別能力，不在量化精度。

## 八、剩餘問題：拇指的有無

這是目前唯一的主要障礙，而且很具體：

| 混淆配對 | 差別 |
|---|---|
| cls1 (食) ↔ **cls7** (拇+食) | 拇指 |
| cls2 (食+中) ↔ **cls8** (拇+食+中) | 拇指 |
| cls3 (食+中+無名) ↔ **cls9** (拇+食+中+無名) | 拇指 |
| cls4 (四指，拇指彎) ↔ **cls5** (五指全開) | 拇指 |

**四組都是「差一根拇指」。** letterbox 讓症狀從「完全忽略拇指」變成「差一級」，但沒有根治。

### 給訓練端的建議

1. **針對這四組配對補樣本** —— 同一隻手、同一個位置，只有拇指張/收的成對影像。這種對比樣本比單純增加總量有效得多
2. **改用 group split**（以拍攝場次切分，不要隨機洗牌）—— 隨機切分會讓同一段連拍的相鄰影格同時落在 train 和 val，mAP 會嚴重灌水
3. **提供逐類別 mAP**，不要只有平均值 —— 平均值會被表現好的類別掩蓋
4. 用 `--save-clean` 收一批**實機域**的測試集，直接評估 `best.pt` 在板子畫面上的表現

## 九、本日的自我修正

紀錄下來避免重蹈：

1. **「三次測試共 253 幀 passThr 全為 0」** —— 後來還原輸入傾印才發現，有些時段畫面裡根本沒有手。那些幀 `passThr=0` 是正確行為，不該當成證據

5. **「每類只有 2 段影片」** —— 那是舊資料集，新的 3000 張在 Johnson 那邊，我沒看到
6. **拿類別次數當成效指標** —— 次數多不代表認對，必須逐張核對實拍圖
