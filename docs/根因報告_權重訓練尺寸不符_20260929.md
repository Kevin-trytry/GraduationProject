# 根因報告：部署端載入了訓練尺寸不符的權重

> 日期：2026-09-29　|　撰寫：Johnson（訓練／匯出端）
> 收件：Kevin（韌體端）
> **本文取代先前所有關於「量化是不是瓶頸」的推論。**

---

## 〇、一頁摘要

從 2026-06 到 2026-09，`export_full_int8.py` 一直讀取一顆 **2026-06-04 用 imgsz=640 訓練**的權重，
但韌體與匯出都以 **192**（更早是 96）運作。

九月所有的板子症狀——滿版退化框、cls2 黑洞、96 完全零偵測、信心度只有 40%——
全部是這個不一致造成的。**訓練端、量化、Vela、韌體後處理都沒有問題。**

換上 2026-09-11 用 192 訓練的權重之後：

| 指標 | 06-04 的 640 權重 | **09-11 的 192 權重** |
|---|---|---|
| 判對率（float，55 張） | 35% | **100%** |
| 正解類別分數 | 0.290 | **0.907** |
| 背景誤偵測率 | 40% | **0%** |
| 預測框面積 | 82.6% | **60.4%** |
| 超過韌體 0.95 過濾門檻 | 26% | **2%** |
| 量化 MAE（float vs INT8） | 0.00042 | **0.00007** |
| bbox IoU（float vs INT8） | 0.932 | **0.978** |
| Vela CPU operators | 0 | **0**（NPU 245，100%） |

框面積 60.4% 與 `check_label_scale.py` 量到的訓練集標註框（45~60%）吻合。
**「滿版退化框」不是 DFL 的問題、不是量化的問題、不是訓練資料的問題。**

**新的 vela 模型已產出，可直接燒錄：`model_export_tools\best_int8_vela.tflite`**

---

## 一、根因

### 1.1 兩個長得很像的資料夾

| 路徑 | 內容 | 狀態 |
|---|---|---|
| `model_output\gesture_model\weights\best.pt` | 2026-06-04、**imgsz=640**、epochs=100、scale=0.5 | **export 一直讀這個** |
| `model_output\weights\best.pt` | 2026-09-11、**imgsz=192**、epochs=120、scale=0.7、translate=0.2 | 實際的最新權重 |

`gesture_model\weights\` 是六月第一次訓練時 Colab 依 `project=OUTPUT_DIR, name="gesture_model"`
建立的路徑。後續的權重都是用 `files.download()` 抓回本機、存到 `model_output\weights\`，
所以**那個舊資料夾從 06-04 之後就沒有再被更新過**，而匯出腳本忠實地讀著它。

Colab 的訓練腳本 `IMAGE_SIZE = 192` 從頭到尾是正確的，**訓練端沒有做錯任何事**。

### 1.2 尺寸不符的量化影響

同一顆 640 權重，用 `check_best_pt.py --sweep` 在不同輸入尺度推論（同一批 60 張影像）：

| imgsz | 判對率 | 平均最高信心 | **平均框面積** |
|---|---|---|---|
| 96 | **9%** | 0.127 | **99%** |
| 192 | 35% | 0.563 | 83% |
| 320 | 73% | 0.634 | 64% |
| **640**（訓練尺度） | **80%** | 0.699 | **58%** |

單調關係，沒有例外。框面積那一欄是最直接的證據：離訓練尺度越遠，框越接近滿版。

### 1.3 為什麼三個月都沒被發現

尺寸不符**不會產生任何錯誤訊息**：

- 模型結構仍然合法，ONNX / onnx2tf / TFLite 轉換全部成功
- Vela 編譯通過，`CPU operators = 0`
- 韌體的 anchor 對帳也過（anchor 數只看 `YOLOV8_OB_INPUT_TENSOR_WIDTH`，與權重無關）
- 唯一的徵狀是「實機表現莫名其妙地差」

## 二、96 完全零偵測框 —— 結案

`除錯報告_開發板零偵測框_20260908.md` 列的五條路徑，前四條當時就排除了，
第五條（mAP 無法證明模型可用）方向對但不是主因。

**真正的原因：這顆 640 權重在 96 的判對率是 9%，框面積 99%。**

所有輸出都是滿版退化框，全部撞上韌體的大框過濾，所以一個框都畫不出來。
與 DFL 均勻分布、與量化校正偏斜、與抽樣步長都沒有關係。

## 三、已排除的路徑（附數據）

### 3.1 INT8 量化 —— 排除

以 60 張未參與校正的影像，同一套前處理，分別跑 float SavedModel 與 INT8 tflite：

| 指標 | 數值 | 判讀 |
|---|---|---|
| cls 輸出飽和比例 | **0.000%** | 沒有任何數值被 clip |
| bbox 輸出飽和比例 | **0.000%** | 同上 |
| 全類別分數 MAE | **0.00007** | 兩張圖的輸出幾乎完全一致 |
| 同一 anchor 的分數誤差 | 0.0088 | 遠低於 0.10 的警戒值 |
| bbox IoU | **0.978** | 框幾乎沒有移動 |
| 框面積膨脹 | **+0.4 pp** | 量化沒有讓框變大 |
| 判對率 float → INT8 | **100% → 100%** | 量化沒有改變任何一張的判斷 |

「精度從 float32 壓到 int8 導致數值被修掉、誤差累積滾雪球」——**在這批資料上不成立**。

補充一個常被誤解的機制：INT8 網路每一層的 MAC 累加是在 **int32 累加器**裡做的，
再依該層的 scale 重新量化回 int8。誤差在每一層都被重新錨定，不會跨層滾雪球。
真正會出事的是「某一層的量化範圍抓錯導致 clipping」，而飽和比例 0% 正是在量這件事。

### 3.2 Vela 編譯 —— 排除

```
CPU operators = 0 (0.0%)
NPU operators = 245 (100.0%)
```

整張圖一顆 `ethos-u`，`MicroMutableOpResolver<2>`（Transpose + EthosU）綽綽有餘。

### 3.3 轉檔鏈路（ONNX → onnx2tf → SavedModel）—— 排除

用 ultralytics 原生 `YOLO.predict()`（無 monkey patch、無轉檔、無自訂前處理）
量同一批 60 張影像，判對率與轉檔後的量測**完全一致（都是 35%，換權重後都是 100%）**。

### 3.4 Layout A vs B —— 非關鍵

Kevin 09-11 的實機對照（平均信心 43% vs 45%）結論「沒有實質差異」成立。
兩者的差別只在輸出層的量化粒度，而根因在輸入尺寸，兩邊同樣受影響。

**匯出格式挑順手的就好，目前用 Layout B。**

## 四、本次推翻的、我自己先前的幾個判斷

誠實記錄，避免之後有人重走這些路：

| 我的推論 | 結果 | 說明 |
|---|---|---|
| 「i.i.d. 切分造成資料洩漏，mAP 0.98 是灌水的」 | **撤回** | 換對權重後訓練域判對率 100%，mAP 0.98 可信。資料是一張一張拍的，不是影片抽幀 |
| 「Layout B 的 DFL 被量化壓平，框會系統性變大」 | **未成立** | 實測框膨脹只有 +0.4 pp |
| 「校正前處理用 center_crop 才對，stretch 是缺陷」 | **無效對照** | 素材是正方形（1440²、3072²、3024²），三種前處理數學上等價 |
| 「資料集尺度單一，需要補拍 1,300 張」 | **降級** | 仍是真問題，但不是擋路的那個。優先度排在實機驗證之後 |
| 「量化保真度用『峰值分數誤差』量」 | **指標錯誤** | 取一個變數的極大值再比另一個變數有選擇偏誤。已改為固定 anchor + 帶號誤差 |

## 五、已加入的防呆

`export_full_int8.py` 新增 **Step 0**：開跑即讀取 checkpoint 的 `train_args`，
核對 `imgsz` 與 `IMAGE_SIZE`，不一致直接丟例外中止。

```
[Step 0] 核對權重的訓練設定...
  檔案      : ...\model_output\weights\best.pt
  訓練日期  : 2026-09-11T04:11:25
  imgsz     : 192
  epochs    : 120
  scale     : 0.7
  translate : 0.2
  [OK] 訓練尺寸 192 與部署尺寸 192 一致。
```

- **只檢查 `imgsz`**，其餘參數僅供核對，訓練怎麼調都不會被擋
- `ALLOW_IMGSZ_MISMATCH = False` 為明確的逃生開關
- 權重超過 30 天沒更新會提醒（防「訓了新的但腳本指著舊的」）
- `himax_vela.ini` 改為多路徑搜尋，不再綁在 `WEIGHTS_DIR` 底下

另附 `find_weights.py`：掃描所有 `.pt`，列出每顆的 imgsz / epochs / scale / 日期。

## 六、仍未解決的項目

### 6.1 Sharpen：訓練有、韌體沒有（Kevin 標紅的問題，答案在此）

Colab 訓練腳本在**切分資料之前**，對所有影像做一次性銳化並**覆蓋原檔**：

```python
A.Compose([A.Sharpen(alpha=(0.2, 0.5), lightness=(0.5, 1.0), p=1.0)])
```

| 項目 | 內容 |
|---|---|
| 函式庫 | `albumentations.Sharpen` |
| 強度 | alpha 0.2~0.5 隨機、lightness 0.5~1.0 隨機 |
| 時機 | **在 resize 之前**，對原始解析度的影像 |
| 機率 | `p=1.0`，每張都做 |
| 性質 | **不是 augmentation**，是一次性前處理覆蓋，訓練全程吃銳化版 |

韌體端沒有做銳化，板子拿到的是 OV5647 原始畫面。這是一個確定存在的訓練／部署不一致。

兩種修法擇一：(a) 韌體補上等效銳化；(b) 訓練端移除 `apply_edge_enhancement()` 重訓。
**建議先不要動**——一次只改一個變因，等新模型上板測完再說。

### 6.2 相機域差異

訓練素材是正方形手機照片，板子是 320×240 取中央 240×240。
正方形素材**無法模擬**這個裁切，只能用板端實拍影像驗證。

→ 需要 Kevin 提供依類別分資料夾的板端實拍影像，設定 `export_full_int8.py`
的 `BOARD_CALIB_DIR`，讓量化區間對準部署域。

### 6.3 資料集尺度單一

`check_label_scale.py`：標註框類別內 P90/P10 僅 **1.1~1.8 倍**，所有樣本都是手貼近鏡頭、
指尖切齊畫面邊緣。09-11 的訓練已用 `scale=0.7, translate=0.2` 補償
（有效縮放範圍 [0.3, 1.7]），但合成的縮小樣本無法還原當初沒拍進去的指尖脈絡。

**是否需要補拍，等實機測試數據再決定。**
> 後續更新：已由 `發現紀錄_尺度不變性量測_20260929.md` 量測並撤回補拍建議。
