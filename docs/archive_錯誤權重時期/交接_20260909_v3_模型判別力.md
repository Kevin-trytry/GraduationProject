## 一、我犯的錯：韌體前處理有幾何失真

09-08 那份報告我寫「韌體已全數排除」，當時漏掉了前處理的幾何。

```
訓練圖片   1440 × 1440   正方形（手機 1:1 模式＝裁切，非壓扁）
Camera raw  320 × 240    4:3
模型輸入    192 × 192     ← 韌體原本直接硬拉
```

硬拉 320×240 → 192×192，水平方向被額外壓縮 **25%**。而 ultralytics 訓練與推論都用 letterbox（等比縮放 + 補灰邊 114），**模型從來沒看過橫向壓扁的手**。

### 怎麼確認訓練圖是裁切而非壓扁

原始素材是混的：`0/3/4/8/B.MOV` 是 1920×1080 (16:9)、`1/2/6.mov` 本來就 1440×1440，抽出來的 jpg 全是 1440×1440。

拿同類別、兩段不同來源影片的**標註框長寬比**互比：

| 類別 | 16:9 來源 | 1:1 來源 | 比值 |
|---|---|---|---|
| 0 | 0.811 | 0.849 | 1.05 |
| 1 | 0.520 | 0.502 | 1.04 |
| 5 | 1.069 | 1.083 | 1.01 |
| 9 | 1.088 | 1.091 | 1.00 |
| B | 3.382 | 3.400 | 1.01 |

若是壓扁，16:9 來源的長寬比應變成 0.5625 倍，比值會出現 **1.78** 左右。實際只有 **1.00~1.15** → **是置中裁切，幾何忠實。**

### 為什麼受害的是拇指類

**拇指是唯一往水平方向伸出去的手指**，壓掉 25% 之後幾乎貼回手掌。失敗類別的分佈本身就是佐證：

| 方向 | 類別 | 修正前 |
|---|---|---|
| 垂直 | 0 拳、1 食指、2 V、3 三指 | ✅ 正常 |
| **水平張開** | 4 四指、5 五指、7/8/9 拇指外張 | ❌ 全掛 |

### 修正與效果

`cvapp_yolov8n_ob.cpp` 加入 `YOLOV8_USE_LETTERBOX`：整片填 114、等比縮成 192×144 寫進中間、上下各 24 列灰邊；後處理座標先扣 `pad_y` 再換算回相機座標。

| session | 標註 | 筆數 | 類別數 | cls3 | **cls4** | cls10 |
|---|---|---|---|---|---|---|
| 15:41 / 15:53 / 16:07 / 16:12 | 前 | 236/334/199/67 | 9/6/6/3 | 20/0/0/0 | **0 / 0 / 0 / 0** | 22/0/0/0 |
| **16:45** | **後** | **540** | **10** | **64** | **118** | **31** |

**cls4 從四場全部掛零 → 118 筆**，最高 93%、有 21 幀連續穩定段。

> 這一段的教訓：**幾何一致性是韌體與訓練之間的隱性契約**。以後你若改變訓練端的 resize / letterbox 行為，一定要告訴我。

## 二、Layout A 已完成，但實機沒有變好

你提供的 Layout A 模型規格完全正確：

```
IN   [1, 192, 192, 3]
OUT  [1, 11, 756]  scale=0.00390625 (1/256) zp=-128   ← class，已 sigmoid
OUT  [1, 4, 756]   scale=1.3856      zp=-120          ← bbox，像素值
operators: ethos-u ×1                                  ← 零 CPU fallback
```

兩個輸出 scale 不同、沒有多餘的 Transpose —— **匯出這一關你做對了，不用再調。**

|---|---|---|

| **平均信心度** | **42%** | **42%** |

### ★ 依序比 1~9 的逐幀核對

17:00 那場我是**依序比 1~9**（後半段才隨機），前 90 秒有明確 ground truth。等間隔取樣 12 幀：

| 時間 | 實際手勢 | 預測 | |
|---|---|---|---|
| 00:24 | one | cls8 31% | ❌ |
| 00:30 / 00:36 / 00:42 | OK 圈 | cls2 87% / 22% / 38% | ❌ |
| 00:48 | one | cls3 68% | ❌ |
| 00:55 | one | cls7 25% | ❌ |
| 01:02 | two | cls4 38% | ❌ |
| 01:08 | two | cls3 28% | ❌ |
| 01:14 | three | cls4 53% | ❌ |
| 01:26 | three | cls3 28% | ✅ |
| 01:38 | four/five | cls4 22% | ✅? |

**12 張裡只有 1~2 張正確。**

同一個手勢的預測會在數個類別間游移（two → cls4 與 cls3；three → cls4 與 cls3）。
**不是固定偏移**（可排除類別索引錯位），是真的分不出手指數量。

### 結論

```
letterbox 前          ：黑洞是 cls2（230 筆）
letterbox + Layout B  ：黑洞是 cls4（118 筆），但有驗證到正確的 cls4 / cls3 / cls10
letterbox + Layout A  ：黑洞是 cls4（157 筆），依序測試下幾乎全錯
```

**黑洞只是換了位置，沒有消失；平均信心度完全沒動（42% → 42%）。**

原本預期「class 量化解析度好 14 倍會讓混淆類別分得開」—— **沒有實現**。
這反過來是很強的資訊：**瓶頸不在量化精度，在模型本身的判別能力。**

## 三、★ 現在請你做的四件事

### 3.1 先確認 `best.pt` 在 PC 上到底有多好（最高優先）

在動任何匯出設定之前，必須先知道 float 模型本身行不行。

```python
from ultralytics import YOLO
m = YOLO('best.pt')
r = m.val(data='dataset.yaml', imgsz=192, split='val', verbose=True)
```

**請回傳逐類別的 P / R / mAP50 / mAP50-95，不要只給平均值。** 平均值會被表現好的類別掩蓋掉 4/5/7/8/9 的崩潰。

如果逐類別 mAP 顯示 2/3/4 之間就已經互相混淆 → **問題在訓練，跟量化無關**，往 3.2、3.3 走。
如果 float 每類都 > 0.9、實機卻是上面那個表 → 才回頭查量化。

### 3.2 validation 改 group split（可能你的 mAP 是灌水的）

`data handling/train_yolo.py`：

```python
random.shuffle(pairs)      # ← 對「全部影像」i.i.d. 隨機洗牌
```

資料是**連拍影格**。隨機切分會讓同一秒內幾乎一模一樣的相鄰影格同時落在 train 和 val，模型在 val 上看到的是它訓練時已經記住的畫面。

**這種切分下的 mAP 衡量的是「有沒有記住」，不是「能不能泛化」。**

改成以拍攝場次／檔名前綴為單位切分：

```python
from collections import defaultdict
groups = defaultdict(list)
for img, lbl in pairs:
    key = img.stem.rsplit('_', 1)[0]     # 依實際命名規則調整
    groups[key].append((img, lbl))

keys = list(groups); random.shuffle(keys)
n = len(keys)
train_keys = keys[:int(n*0.8)]
val_keys   = keys[int(n*0.8):int(n*0.9)]
test_keys  = keys[int(n*0.9):]
```

**改完重新評估。如果 mAP 掉很多，那就找到真正的問題了。**

### 3.3 針對混淆配對補「成對樣本」

實機上互相混淆的組合：

| 混淆配對 | 差別 |
|---|---|
| cls1 (食) ↔ cls7 (拇+食) | 拇指 |
| cls2 (食+中) ↔ cls8 (拇+食+中) | 拇指 |
| cls3 (食+中+無名) ↔ cls9 (拇+食+中+無名) | 拇指 |
| cls4 (四指，拇指彎) ↔ cls5 (五指全開) | 拇指 |
| **cls2 ↔ cls3 ↔ cls4** | **手指數量本身** |

最後一組是今天新增的發現 —— 不只是拇指，**連伸出幾根手指都分不出來**。

建議：**同一隻手、同一個位置、同一個光線，只有手指數量不同的成對／成組影像。** 這種對比樣本比單純增加總量有效得多。3000 張如果全是各自獨立拍的，模型學到的可能是「拍攝場次的背景差異」而不是手指。

### 3.4 用實機域測試集評估
