## 二、已排除的路徑（附證據）

### ❌ 路徑 3：`AllocateTensors()` 靜默失敗 — 排除

v2 推測「96 尺寸讓 vela 把 Reshape / Quantize 等 op 留在 CPU，而 `MicroMutableOpResolver<2>` 沒註冊，導致 AllocateTensors 失敗」。

直接解析燒錄用的模型檔（`gesture_yolov8n_96_vela_0xB7B000.tflite`）：

```
subgraph operators : 1
  ethos-u  x1          ← 整個網路一顆 op，連 Transpose 都沒有
```

**零 CPU fallback。** `MicroMutableOpResolver<2>`（Transpose + EthosU）綽綽有餘，不會註冊失敗。

記憶體也排除：

| | 執行期 tensor 需求 | arena 可用 |
|---|---|---|
| 新 96 模型 | **124.4 KB**（scratch 83.6 + 輸入 27.0 + 輸出 13.8） | 1053 KB |
| 舊 192 模型 | 949.9 KB（scratch 830.8 + 輸入 108.0） | 1053 KB |

值得注意的是**舊的 192 模型才是貼著 arena 上限跑的（950/1053）**；96 只用了 1/8，不可能因記憶體不足而失敗。

> #### ⚠️ v2 的判斷依據方向相反 — 已更正
>
> v2 寫「有 `initial done` 但沒有 `invoke pass` → 確認是此問題」。
>
> 實際上 `xprintf("initial done\n")` 位在 `return false` **之後**，AllocateTensors 失敗時會提前 return，**`initial done` 根本不會印出來**。
>
> 正確判讀是：**`initial done` 沒印 → init 中途失敗**。

#### Bug 本身是真的，已修

v2 指出的 `return false`（= 0 = 成功碼）確實存在，而且比 v2 描述的更嚴重 —— **呼叫端 `tflm_yolov8_od.c` 根本沒接回傳值**：

```c
cv_yolov8n_ob_init(true, true, YOLOV8_OBJECT_DETECTION_FLASH_ADDR);  // 沒有 if
```

已修（不採用 v2 建議的「加大 op resolver 容量」，因為模型只有一顆 op，加了也沒用；改為讓失敗變得大聲）：

| 檔案 | 改動 |
|---|---|
| `cvapp_yolov8n_ob.cpp` | 兩處 `return false` → `return -1`；AllocateTensors 失敗時印出 arena 大小、arena 位址、model 位址 |
| `cvapp_yolov8n_ob.cpp` | `cv_yolov8n_ob_run()` 補 `else` 分支：ptr 為 null 時印 `[FATAL] interpreter is NULL`（限前 5 幀，不洗版） |
| `tflm_yolov8_od.c` | 呼叫端加回傳值檢查 + `[FATAL] cv_yolov8n_ob_init failed!` |

以後這條路徑若真的發生，會直接在 log 上喊出來，不需要再靠推理。

### ❌ 路徑 4：sigmoid 判斷誤判 — 排除

實測 96px 模型的 class tensor 量化參數：

```
scale = 0.16959,  zero_point = 4
cls_max_repr = (127 - 4) x 0.16959 = 20.86  >  1.5   →  正確判為 logit
```

判定邏輯正常，`sigmoid=YES (韌體補算)` 會成立。

> v2 附註「參考值：192px 模型的 `scale=0.169, zp=4`」—— 這組數字其實是 **96px** 模型的。192px 模型是 `scale=0.209, zp=38`（`cls_max_repr = 18.6`）。兩者都遠大於 1.5，結論不變。

## 三、★★ 新增路徑 5：mAP 0.982 不足以排除訓練端

v2 的結論「**訓練端已排除，問題 100% 在部署端**」下得太早。mAP 0.982 是在**驗證集**上量的，而這個驗證集有兩個問題：

### 3.1 切分方式造成資料洩漏

`data handling/train_yolo.py`：

```python
def split_dataset(pairs, train_ratio=0.80, val_ratio=0.10, seed=42):
    random.seed(seed)
    random.shuffle(pairs)      # ← 對「全部影像」做 i.i.d. 洗牌
    ...
```

`collect_pairs()` 把 11 個資料夾底下的影像攤平成一個 list，再整包隨機洗牌切 80/10/10。

資料集約 1226 張，是**同一批連拍**的影格。隨機切分會讓**同一秒內、幾乎一模一樣的相鄰影格同時落在 train 和 val**。模型在 val 上看到的其實是它訓練時記住的畫面。

**這種切分下的 mAP 主要衡量「有沒有記住」，不是「能不能泛化」。** 0.982 這個數字在這個切分方式下是預期中的，並不能證明模型的能力。

> 正確做法是 **group split**：以拍攝場次／檔名前綴為單位切分，確保同一段連拍只會出現在其中一邊。這是訓練端可以立刻改善的地方。

### 3.2 相機域差異（domain gap）

驗證集與訓練集是同一台相機（手機／一般相機）拍的。板子上是 **OV5647 + 320×240 datapath + 縮到 96×96**，色彩、雜訊、動態範圍、鏡頭畸變全都不同。

`Analysis/detection_analysis_20260901.md` 已經記錄過這個現象；`training_param_guide.md` 加大 `hsv_v` / `hsv_s` 增強就是為了補償它。**這類 domain gap 造成「val 接近滿分、實機接近零」是很典型的**。

### 3.3 這條路徑要怎麼驗證

**決定性實驗（不需要燒板子）**：請 Johnson 提供 **Vela 編譯前**的 `best_full_int8.tflite`（96 版本）。Vela 模型只能在板子上跑，但編譯前的 int8 tflite 可以在電腦上跑。

拿它去推論 `captures/` 底下的**實拍照片**（那些是 OV5647 真的拍到的畫面），一次就能分辨：

| 結果 | 結論 |
|---|---|
| 實拍照片上也偵測不到 | **模型的問題** —— val mAP 是假象，需要 group split 重新評估 + 補實機域的訓練資料 |
| 實拍照片上偵測得到 | **部署端的問題** —— 回到路徑 1 / 2 |

順帶請他提供**逐類別的 mAP**（Ultralytics 的 `val()` 會印每一類的 P/R/mAP50），而不只是平均值。v2 用平均值反推逐類別能力的推論在資料洩漏的前提下不成立。

## 五、路徑 2（大框過濾）— 升級，已調整參數

v2 的機制推導是對的，而且比 v2 自己估的更嚴重。

### 5.1 實測數據

`captures/session_20260908_200935`（192px 模型，256 筆偵測）的框面積佔畫面比例：

| P10 | P25 | **P50** | P75 | P90 | P95 | P100 |
|---|---|---|---|---|---|---|
| 56% | 66% | **77%** | 90% | 97% | 99% | 99.6% |

排除大框後的 147 筆（也就是被判定為「正常」的框）：

- 中位數 **67.8%**、平均 65.3%、**最大 79.7%**
- 換算成 96×96 的邊長：中位數約 79px、**最大約 86px**
- 0.80 面積門檻對應邊長 = **85.9px**

**正常框的最大值 79.7% 幾乎就等於 0.80 的門檻 —— 餘裕是零。** 在目前的拍攝距離下，手就是佔畫面 70~80%，門檻設 0.80 隨時會誤殺。

### 5.2 v2 表格的一處修正

v2 表格暗示「同一個比例在 96 下比在 192 下嚴格」。實際上**面積比例不隨輸入尺寸改變**（w、h 同時等比縮放，比例恆定），所以 0.80 在兩個尺寸下一樣嚴格。

但 v2 表格本身的推導是對的，真正的差異在**退化框**：

| stride | 均勻 DFL 解碼框 | 192 輸入 | 96 輸入 |
|---|---|---|---|
| 8 | 7.5 × 8 × 2 = 120px | 120×120 = 39% → **通過** | 夾回 96×96 = 100% → **被丟** |
| 16 | 7.5 × 16 × 2 = 240px | 被丟 | 被丟 |
| 32 | 7.5 × 32 × 2 = 480px | 被丟 | 被丟 |

也就是說：**在 192 下，stride 8 的退化框會通過過濾、被當成偵測畫出來；在 96 下三層的退化框全部被丟。** 如果模型在實機上多半只輸出退化框，192 會看到一堆亂框、96 則是完全沒框 —— 這與觀察到的現象吻合。

### 5.3 已套用的修改

```c
// cvapp_yolov8n_ob.cpp
#define YOLOV8_MAX_BOX_AREA_RATIO 0.95f   // 原 0.80f
```

0.95 仍能擋掉真正的整張畫面框（分布中 ≥99% 的那 11 筆），但保留貼近邊界的正常框。註解裡已寫入上述分布數據作為調整依據。

> v2 建議「先設 1.0f 驗證」。不建議 —— 1.0f 等於關閉過濾，全畫面框會回頭在 NMS 吃掉正確框（IoU ≈ 0.52 > 0.45），反而製造新的假象。0.95f 已經足夠寬鬆到能驗證，又不會引入這個副作用。

## 七、UART log 判讀（修正版決策樹）

```
有 [FATAL] 開頭的訊息嗎？
├─ 有 ─────────────────────→ init 失敗，訊息本身會說明原因（arena / op / model addr）
└─ 沒有
   └─ 有 "initial done" 嗎？          ← 注意：失敗時「不會」印，v2 寫反了
      ├─ 沒有 ────────────────→ init 中途 return（現在會有 [FATAL] 指出位置）
      └─ 有
         └─ 有 "invoke pass" 嗎？
            ├─ 沒有 ─────────→ interpreter 為 null（現在會印 [FATAL] interpreter is NULL）
            └─ 有
               └─ num_anchors = ?
                  ├─ 756 ────→ 路徑 1：燒到舊快照
                  ├─ 189
                  │  ├─ 大量 [filter] drop（0.95 之下）─→ 模型只輸出退化框 → 路徑 5
                  │  ├─ 無 [filter]、[CLS-DBG] 全個位數 ─→ 路徑 5：模型在實機域無反應
                  │  └─ 無 [filter]、[CLS-DBG] 有高分 ──→ 門檻或 NMS 問題，回報給我
                  └─ 沒印 layout log ─────────────────→ 後處理沒進入，回查 [FATAL]
```

### 需要的 log 行

| log 行 | 判斷什麼 |
|---|---|
| `TA[xxxx]` | tensor arena 分配 |
| `Ethos-U55 device initialised` | NPU 初始化 |
| `yolov8n_ob model's schema version` | 模型讀取成功 |
| **`[FATAL] ...`** | **新增，init 失敗會直接指出原因** |
| `initial done` | init 完整跑完（**沒印 = 失敗**） |
| `raw info: w[] h[] ch[] addr[]` | 相機正常（w=320 h=240 ch=3，addr ≠ 0） |
| `yolov8 object detect invoke pass` | 推論有跑 |
| `=== YOLOv8 OUTPUT LAYOUT ===` 整段 | `num_anchors` 189 / 756、`sigmoid=` |
| `[CLS-DBG] ... scores%:` | 模型對各類別的反應 |
| `[filter] drop oversized box` | 大框過濾狀況 |
| `boxes.size(): N` | 過完濾之後剩幾個框 |

## 八、其他觀察（零框解決後再處理）

### Score Threshold
目前 `0.20`。v2 建議零框解決後調高至 0.35~0.50 —— **同意方向，但先不要調**。理由：在確認模型於實機域的實際信心分布之前調高，會把路徑 5 的症狀誤判成「調對了」。先用 `[CLS-DBG]` 收集真實分布再決定。

### 改用 Layout A
v2 的建議成立且值得做。目前 96 模型兩個輸出共用 `scale = 0.16959`，class logit 每階 0.1696 → sigmoid 後在 0.5 附近約 **4.2 個百分點**一階。Layout A 的 class 輸出是已 sigmoid 的 0~1、`scale = 1/256` → 每階 **0.39 個百分點**，解析度差約 **11 倍**。

而且**韌體不用改**，會自動偵測並走 Layout A 分支。

### 三端參數對接（v3 複核）

| 項目 | train | export | cvapp | 狀態 |
|---|---|---|---|---|
| IMAGE_SIZE | 96 | 96 | 96 | ✅ |
| NUM_CLASSES | 11 | 11 | 11 | ✅ |
| NUM_ANCHORS | — | 189 | 自動推算 189 | ✅ |
| 輸出格式 | — | `[1,64,189]`+`[1,11,189]` Layout B | 自動偵測 | ✅ |
| 輸入量化 | — | int8, scale 1/256, zp −128 | 不檢查 | ✅ |
| 類別順序 | `['0'..'9','B']` | — | `{"0".."9","B"}` | ✅ |
| Flash 位址 | — | 不需知道 | `0x3AB7B000` / offset `0xB7B000` | ✅ |
| **驗證集切分** | **i.i.d. random shuffle** | — | — | **⚠️ 見 §3.1** |

程式碼層面三端確實對齊，v2 這點成立。但**「對齊」只保證資料格式能通，不保證模型在實機域有效** —— 那是 §3 要處理的事。
